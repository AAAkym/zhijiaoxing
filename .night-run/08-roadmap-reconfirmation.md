# 08-roadmap-reconfirmation.md · 未来方向的二次确认与细化解释

> 本文件是对 `05-roadmap.md`（R-1 ~ R-8）的**逐条二次确认**。
> 每条给出：**第一轮的说法 → 第二轮新增的证据 → 结论（保留 / 调整 / 降级 / 升级）→ 细化解释**。
>
> 二次确认的原则：第一轮的判断若在第二轮被新证据推翻或加强，必须**显式改口**，
> 不能默默沿用。凡是标注"未验证"的，第二轮没有造出证据就继续标注"未验证"。

## 一句话结论

第一轮的方向**没有一条被证伪**，但**优先级的相对顺序发生了实质变化**：
R-5 从"强烈建议"升级为**唯一的"立刻做"**，因为第二轮找到了它所要防的那类缺陷的
**两个活体样本**（不是假想）。R-1 的价值判断不变，但它的**前置依赖被揭示**：
它依赖的数据契约在第一轮并未被测试覆盖。R-3 仍然"未验证"，且第二轮**再次**没有为它造数据。

## R-1 · 「依据链 → 干预动作」闭环

**第一轮说法**：后端批量生成链路已存在且有测试，成本低，演示性极高。

**第二轮新增证据**：
- 后端链路**确实存在**：`backend/src/routes/resource_generation.py` 下有完整的
  `class-batches` 流程 —— `preflight` → `class-batches`(POST) → `generate` → `publish`，
  共 7 条路由。第一轮的判断成立，不是想象。
- 但暴露了一个第一轮没看到的事实：`src/components/` 下的组件**大量使用**
  `'../services/api'` 这类相对导入，而 jest 的 `moduleNameMapper` 对
  深度 ≥2 的相对路径**无法可靠拦截**，组件会静默打到**真实实现**并发出真实网络请求。
  这意味着：任何"新增一个前端调用点"的工作，都可能踩到这个坑。

**结论：保留为"下一轮首选功能"，但必须先做一件前置小事。**
前置事项：把 `src/components` 下的 API 导入**统一为 `@/services/api` 别名**
（本轮已顺手改了 3 个文件作为示范；剩余文件仍可在需要时逐个改）。
理由：否则 R-1 新加的前端按钮在测试里会绕过 mock、发出真实请求，
表现为"测试偶发失败"或"断言调用次数为 0"，而报错完全指不到根因 ——
这正是本轮花掉最多时间的那类问题。

**细化解释（为什么这条最值得做）**：
系统当前有两条独立的能力链：**解释链**（为什么给这个学生这份资源）和
**干预链**（按班级薄弱点批量生成资源）。两条链各自都完整、都有测试，
但**中间没有连起来**。从产品角度，一个只能解释不能干预的系统，
对教师的实际价值是"看板"而非"助手"；而两条链都已存在，
连接它们的成本远低于各自重建，这是典型的**高杠杆低成本**改动。

## R-2 · 依据链的「可信度阈值」告警

**第一轮说法**：成本低，纯只读聚合，与 R-1 同批。

**第二轮新增证据**：无直接新增。但与 R-5 的联动被确认 ——
该聚合若落地，需要一条"契约测试"来锁定 `profile_confidence_summary` 字段的存在性，
否则会重演"新增字段但没人用/没人测"的情况。

**结论：保留，与 R-1 同批，但顺带补契约测试。**

**细化解释**：这里的关键不是"加一个统计字段"，而是**把隐性失效变成显性问题**。
当前系统的画像可信度是"每人各自低可信"，教师需要逐个点开才能发现。
聚合成"本班 7 人可信度低于阈值"之后，问题才有行动起点。
注意：**只做聚合展示，不要自动干预** —— 自动干预会把"数据不足"
升级成"用不足的数据做了决策"，风险性质完全不同。

## R-3 · 执行历史 → 「失败归因」下钻

**第一轮说法**：需要先造真实失败记录来验证，否则又是"看起来能用"。

**第二轮新增证据**：**仍然没有**。实测确认 `agent_execution_logs` 167 条
（coordinator 96 / document 27 / project 16 / media 11 / recommendation 11 / exercise 6）
**全部为成功记录**，库里不存在任何失败样本。

**结论：保留，但明确降级为"未验证方向"，且第二轮重申该判断。**

**细化解释**：这条最容易被误当成"低难度小功能"而直接开做，
然后交付一个从没在真实失败数据上跑过的聚合接口 ——
这恰恰是本仓库反复出问题的模式（第一轮的 `resourceGeneration` 导出就是这样：
代码写了、测试绿了、构建是坏的）。
若要做，**第一步应该是构造失败记录**（可以在测试里注入，
但必须同时明确：测试里注入的失败与真实运行时的失败**结构未必一致**）。

## R-4 · 统一入参校验层

**第一轮说法**：最系统性的技术债；建议逐路由增量套用，不要一次性全改。

**第二轮新增证据**：**再次得到印证，且证据更强**。
本轮为 BUG-D 补回归测试时确认，`get_class_learning_groups` 对
`course_id` **完全不做存在性校验**，任何整数都原样透传
（`?course_id=987654321` 返回 200 + 空分组）。
另外该路由用 `request.args.get("course_id", type=int)`，
在畸形输入（如 `?course_id=abc`）下**静默变成 None**，
然后回落成"班级自身课程" —— 用户输入了错的参数，
系统却按"你没传"处理，**这是真实存在的语义混淆**。

**结论：保留，优先级维持中高，且"增量套用"的建议不但不变，反而更应坚持。**

**细化解释**：`type=int` 的静默 None 是典型的
**"三种状态被压成两种"**：没传 / 传了垃圾 / 传了 0，后两者无法区分。
它不会报错，只会给出一个"看起来合理"的结果 —— 这类缺陷最难被用户发现，
因为他们拿不到任何错误提示。统一校验层的价值不在于"代码更整洁"，
而在于**把静默的错误输入变成显式的 4xx**。
之所以强调增量：一次性改几十条路由会产出巨大 diff，
使 review 失效、回滚困难，反而违背了"最小可回滚"。

## R-5 · 把「防静默失效」变成 CI 门禁 ⬆️ 升级为第一优先级

**第一轮说法**：强烈建议，成本极低（三件事都很便宜）。

**第二轮新增证据（关键改口）**：
第一轮只有**一个**样本（`resourceGeneration` 导出不存在，测试绿而构建红）。
第二轮找到了**第二个、而且更严重的同类样本**：

> `frontend/jest.config.js` 里有一份硬编码的 `testPathIgnorePatterns`，
> 把 **6 个测试文件、共 102 个用例**整体排除在外。
> **被排除的套件既不算通过、也不算失败** —— 它们在报告里根本不出现。
> 于是"124 个用例全绿"这句话在字面上是真的，在含义上却是假的。

这比第一轮的样本严重得多：`resourceGeneration` 至少还会让**构建**失败，
而测试文件被排除**不会让任何东西失败**，它会一直安静地待在那里。

**结论：升级。从"强烈建议"改为"立刻做"，并且是本次所有方向中的第 1 名。**
本轮已经完成了其中两件事（见下），第三件仍待办。

**本轮已落地**：
1. **`verify_all.ps1`** —— 把 `jest` + `vite build` + `pytest` 绑定成一次动作，
   任一失败即整体 `exit 1`。第一轮把它列为"建议 1"，本轮已实现并验证通过。
2. **移除全部文件级排除**，让 102 个用例重新进入统计；
   `testPathIgnorePatterns` 现在只保留 `node_modules` / `dist` / `build` 三类
   —— 这三类是**必然无关**的目录，而不是"当前跑不过就先关掉"的文件。

**仍待办（第三件）**：
后端已有 `test_route_registration.py`（9 条用例，覆盖路由注册与
"API 路径不得回落到 SPA"），建议再补一条**参数化测试**：
遍历所有 blueprint 的每条规则，断言"未认证访问 /api/* 必须返回 JSON 而非 HTML"。
理由：本轮已确认后端**不存在**同类隐藏排除
（无 `pytest.ini`/`setup.cfg`/`tox.ini`，`conftest.py` 内无 `ignore`/`deselect`/`addopts`，
167 条用例全部被收集 = 166 passed + 1 skipped，数字自洽），
所以后端的风险不在"被排除"，而在"**注册了但行为不对**"。

**细化解释（为什么这条压过所有功能方向）**：
功能方向做错了，用户会发现（功能不工作）。
**测试基础设施错了，所有人都不会发现** —— 包括未来的维护者，
他们会基于"测试全绿"这个假事实做出错误的技术决策。
第二轮的实际经历就是证明：修好排除项之后，立刻暴露出 105 个失败用例，
其中包含真实的组件缺陷（防抖计时器不清理、多个交互元素无可访问名）。
这些缺陷**已经存在很久了**，只是一直被"全绿"掩盖着。
一条会说话的失败测试，价值高于十个沉默的通过测试。

## R-7 · 结构化日志 / 可观测性

**第一轮说法**：未定位到 sqlalchemy echo 的开启位置。

**第二轮新增证据**：本轮跑完整后端套件时确认，
测试输出的 **2041 条 warning** 里绝大部分是 `LegacyAPIWarning`
（`Query.get()` 已废弃）与 `DeprecationWarning`
（`datetime.utcnow()`），**它们淹没了真正有用的信息** ——
定位一条真实报错需要在这两千条里翻找。

**结论：保留，优先级不变，但**建议先做一件更小的事**：收敛测试期告警。

**细化解释**：可观测性的本质是**信噪比**，不是"有没有日志"。
当前不是缺日志，而是噪声太多导致信号读不出来。
在 `pytest.ini` 或 `conftest.py` 里过滤掉已知的第三方废弃告警，
是低风险、可立即见效的一步；等到能一眼看到真实告警之后，
再做"请求 ID 贯穿 / 慢查询记录"这类真正的可观测性建设才有意义。
否则新增的日志只会汇入同一片噪声。

## R-8 · 会话与密钥治理（阻塞于 SEC-001 / SEC-002）

**第一轮说法**：顺序必须是 轮换密钥 → 清理 git → 补 `.env.example`，
且轮换 `SECRET_KEY` 会让全部会话失效，需低峰期执行。

**第二轮新增证据**：无变化，**仍冻结**。本轮未读取、未修改 `.env`，
也未触碰 `config.py` 中的硬编码 PPT 凭据。

**结论：不变，保持阻塞，顺序不可调换。**

**细化解释**：这三步的顺序是有硬约束的，不能并行或颠倒 ——
**先清理 git 再轮换密钥**是无效的，因为泄露的密钥早已存在于历史提交中，
清理工作区并不能撤销已经外泄的凭据；反过来，
**先轮换再清理**才能保证"清理时那些凭据已经作废"。
另外 `SECRET_KEY` 轮换会让所有已登录会话立即失效，
这是**面向用户的可见影响**，所以必须在低峰期做，且需要提前告知。

## 被判定为"低价值/不做"的（二次确认）

第一轮列出的四条（向量数据库、时序库拆分、全项目 ESLint 大扫除、
前端组件库替换）**第二轮没有出现任何推翻它们的证据**，维持原判。

特别重申**全项目 ESLint 大扫除**这一条：
第二轮改动 16 个文件、492 行新增，之所以能清晰 review、能逐条解释每个改动的原因，
正是因为 diff 里**没有**夹带无关的格式化噪音。
如果先做大扫除，本轮的每一个改动都会淹没在数千行无意义 diff 里，
"哪些改动是必要的"这个问题将无法回答。**这不是洁癖，是审查可行性问题。**
