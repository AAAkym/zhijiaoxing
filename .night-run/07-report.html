一个必须澄清的「非 bug」

BUG-014（SSE 返回 200）需要澄清，不应简单地当成缺陷修。 EventSource 在浏览器端无法读取非 2xx 响应的响应体， 因此「用 200 + error 事件帧」是 SSE 的常见做法。上一轮把它列为问题， 是站在「HTTP 语义正确性」视角；两种视角都成立。

若要让网关识别失败，正确做法是新增一个响应头（如 X-SSE-Auth: failed） 或新增一个并行探测端点，而不是改既有端点的状态码—— 那属于对外契约变更。已记入 03-deferred.md。

4 · 今夜交付的 3 个功能

按任务书第 2 节要求「重心是深度，不是广度」，3 个功能全部做到可演示、可验收、带测试。

功能一 · 生成依据链（Generation Basis Chain）多 Agent 协作

它解决什么问题。答辩最常被追问的一句是「你的个性化是真的吗」。 这个功能让学生点开任意一份学习资源，就能看到这份资源为什么是给他的： 哪些画像维度起了作用、命中了哪些知识点、关联了哪几道错题、质量分是多少、下一轮策略是什么。

多 Agent 体现在哪。coordinator_agent._backfill_execution_evidence 把资源包里 9 个智能体的执行记录回填成 basis_refs / knowledge_point_ids / mistake_ids / quality_score， 依据链直接消费这些证据。

诚实性设计（第一验收项）。缺证据时显式标注而不是编造：

  • 拿不到错题明细（只有聚合计数）→ mistake_evidence 返回空数组， 并在 gaps 中登记 missing_mistake_detail， 绝不用聚合数字伪造错题条目。
  • 难度对齐评分为占位值 75 → 登记 difficulty_alignment_is_placeholder。
  • 画像维度可信度 < 60 → 前端标为「低可信」，不当作确定结论。
  • media / ppt 故意跳过知识库引用 → 不出引用覆盖率结论。

功能二 · 班级学习类型分组多 Agent 协作

它解决什么问题。教师面对一个班，需要知道「这批学生分成哪几种学习类型、 共同薄弱点是什么、该怎么补救」，而不是逐个点开画像。

关键设计：证据不足的学生必须被如实列出，而不是被编造特征。 画像完整度 < 40 或可信度 < 50 的学生进 ungrouped_students， 并给出 reason: evidence_insufficient。少于 2 人的组并入「混合型」。

分组结果是确定性的（rule_based_dominant_dimension）， 用主标签 → 次标签 → 第三标签的顺序，不引入任何聚类库（铁律 4）。

功能三 · 智能体执行历史看板今夜新增工作流

发现这个缺口的经过（有据可查）。我读 agent_execution_logs 表时发现 167 条真实执行记录（coordinator 96 / document 27 / project 16 / media 11 / recommendation 11 / exercise 6），但没有任何读取入口：

  • GET /agents/status 返回的是 AgentMonitor 的内存态， 服务一重启就归零。实测证据：内存态 total_tasks = 0， 而库里躺着 167 条记录。
  • coordinator_agent 把 9 个 Agent 的 execution_details 打进资源包， 但视图层没有任何组件消费它——这份证据事实上是死的。

这个功能补上的就是这条「持久化 → 可视化」的链路。

最核心的设计：六阶段流水线「证据覆盖率」

这个功能没有停留在「列出 167 条记录」。它把真实的六阶段流水线 （GENERATION_STAGES）与执行记录对齐，算出一个覆盖率—— 而这正是「防静默失效」在产品层的表达：

coverage_rate = 有执行证据的必需阶段数 / 必需阶段总数
  • 分母只算真正应当留下执行记录的阶段。quality / package 是协调器内部纯计算，标为 evidence_required: false， 不计入分母（否则会制造虚假缺口）。
  • 拿不到证据的阶段进 stages_without_evidence，前端必须显式点名， 绝不静默按「通过」处理。
  • 空态文案刻意写成：「这不代表系统故障，但也不代表流水线正常—— 没有记录时无法判断协作是否发生。」

最后一条是刻意的：本仓库的失效模式就是「安静地坏掉」，所以空态也必须说清它不能证明什么。

根因：Jest 以 CommonJS 加载源码，import.meta 是 解析期语法错误。

这正是任务书 1.4 节描述的失效模式：套件名看起来存在， 实际一条断言都没跑，而 CI 只看到「1 failed」，很容易被当成偶发。

🔁 自我纠错记录（保留原始误判）。 我第一反应是「加 typeof 守卫就行」，写成： 
const viteEnv = typeof import.meta !== 'undefined' ? import.meta.env : undefined
实测失败，报错仍指向 import.meta。

误判原因：我把它当成运行时未定义来处理， 实际它是解析期语法错误——CJS 解析器看到 import.meta 这个 token 就报错， 根本不会执行到 typeof。正确修法是改用普通标识符 import_meta_env，由 Jest 配置注入。
