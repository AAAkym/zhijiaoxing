## 一、本轮已验证、可直接继续做的（证据最强）

### R-1 · 「依据链 → 干预动作」闭环 🥇 建议优先

**观察到什么**
本轮已经做到：学生能看到"这份资源为什么给我"（`ResourceBasisPanel`），
教师能看到"班级分成哪几种学习类型 + 共同薄弱点"（`ClassLearningTypesPanel`）。
但**两者都止步于"展示"**——教师看到"循环结构掌握度 0.54、2 人"之后，
系统没有提供"针对这个薄弱点给这 2 人补一组练习"的一键动作。

**能做什么**
在 `ClassLearningTypesPanel` 的 `common_weak_points` 行上新增一个"定向补救"按钮，
调用**已存在**的 `mastery_batch` / `class-batches` 链路，把
`{class_id, course_id, knowledge_point, student_user_ids}` 传下去生成定向任务。

**成本与风险**：**低**。后端批量生成链路已存在且有测试；
本轮只需新增一个"把薄弱点映射成生成参数"的纯函数 + 前端按钮。
不新增依赖、不改 schema。

**演示性**：**极高**。"教师端看到问题 → 一键生成针对性任务 → 学生端收到并看到依据链"
是一条完整可演示的闭环，正好回答答辩最常问的"你的个性化到底怎么落地"。

### R-2 · 依据链的「可信度阈值」告警

**观察到什么**
`generation_basis_service.LOW_CONFIDENCE_THRESHOLD = 60`，
前端 `ResourceBasisPanel` 已会把低可信维度标为"低可信"。
但目前**只有展示，没有聚合**：教师无法一眼看出"我班上多少个学生的画像可信度低于阈值"。

**能做什么**
在班级分组接口里**新增**一个 `profile_confidence_summary` 字段
（向后兼容的新增字段，符合铁律 3），统计各可信度区间人数，
并在教师端提示"这 N 个学生的依据链可信度偏低，建议先补充画像"。

**成本与风险**：**低**。纯只读聚合，`build_class_learning_groups` 已在读同样的画像。

### R-3 · 执行历史 → 「失败归因」下钻

**观察到什么**
本轮新增的 `/agents/history` 已经返回 `error_message`（实测库里 167 条全为 success，
所以这条路径**尚未有真实数据验证**，属"设计了但未在真实失败上跑过"）。
`AgentExecutionLog` 表**已有** `error_message` 与 `task_type` 字段，
但没有任何地方按错误类型做聚合。

**能做什么**
新增只读聚合：按 `task_type` × `error_message` 归一化后分组，
给出"哪一类任务最容易失败、典型错误是什么"。

**成本与风险**：**低**。纯查询。**但必须先造出真实的失败记录来验证**，
否则又是"看起来能用"的功能——这正是本仓库反复出问题的地方。

## 二、工程健壮性方向（本轮已有强证据）

### R-4 · 统一入参校验层 🥈

**观察到什么**（继承上一轮结论，本轮在 `_parse_int_arg` 上再次得到印证）
本轮我新增端点时，`request.args.get("limit", 50, type=int)` 这个**仓库里到处都在用**的
写法，无法区分"没传"、"传了 0"、"传了垃圾值"三种情况——我不得不专门写一个 helper。
同理 `request.get_json()` 在畸形 JSON 上的行为也各路由不一。

**能做什么**
一个 `@validate_query(...)` / `@validate_json(...)` 装饰器，
把"用户错误 → 4xx + 人话提示"变成默认行为。

**成本与风险**：**中**。会触及大量既有路由（属"新增装饰器"而非"改主流程"，
但落地时容易变成大范围改动）→ 建议**逐路由增量套用**，不要一次性全改。

**优先级**：中高。这是本仓库最系统性的技术债。

### R-5 · 把"防静默失效"变成 CI 门禁 🥉 强烈建议

**观察到什么（本轮最有价值的教训）**
本轮我踩到一个教科书级案例：
`AgentExecutionHistoryPanel.jsx` 导入了 `api.js` 里**不存在**的 `resourceGeneration`。
- `pnpm test` **全绿**（因为测试 mock 掉了整个模块，mock 里恰好也叫这个名字）
- 只有 `pnpm run build` 才报错

也就是说：**这个仓库的测试通过，不代表代码能构建**。
同理，后端"路由没注册"也无法被现有测试发现（已由 `test_route_registration.py` 部分补上）。

**能做什么**（三件，都很便宜）
1. **把 `pnpm run build` 纳入验收脚本**——本轮已证明它能挡住 `pnpm test` 挡不住的错。
2. 保留并扩展本轮新增的 `apiExportContract.test.js`（已证明能捕获该类 bug）。
3. 后端已有 `test_route_registration.py`；建议再补一条"
   **每个 blueprint 的每条规则都必须返回 JSON**"的参数化测试。

**成本与风险**：**极低**。纯测试与脚本。
