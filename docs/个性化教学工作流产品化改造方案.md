# 智教星个性化教学工作流产品化改造方案

## 一、文档目标

本次改造不以答辩展示或比赛包装为主要目标，而是把现有的学生画像、知识图谱、资源生成、练习评测和学习路径连接成一套可以持续使用的教学产品。

产品需要解决的核心问题不是“能不能生成资源”，而是：

```text
教师怎样发现学生的问题
→ 系统怎样制定有依据的学习方案
→ 教师怎样确认并发布任务
→ 学生怎样完成学习
→ 系统怎样判断学生是否真正掌握
→ 后续教学怎样根据结果自动调整
```

产品核心定位：

> 智教星是一套由真实学习证据驱动的个性化教学工作流。系统负责诊断、制定方案、生成资源和评估效果，教师负责关键决策，学生完成具体学习任务，最终形成持续更新的教学闭环。

---

## 二、需要先明确的事实与限制

### 2.1 当前已经具备的基础

根据现有项目代码和文档，系统已经包含以下能力：

- 八维学生画像及画像对话。
- 练习、错题、编程、视频和互动行为数据。
- 课程知识图谱和课程知识库。
- 文档、习题、项目等多类资源生成智能体。
- 学习路径、练习评测、错题反馈和学情分析模块。
- 教师、学生和管理员三类角色及基础权限体系。

这些能力为工作流提供了基础，但“存在这些模块”不等于“已经形成完整工作流”。目前仍需验证和打通各模块之间的数据传递与状态转换。

### 2.2 当前约束

本阶段继续遵守数据库保护原则：

- 不新增数据库表。
- 不修改现有字段。
- 不执行数据库迁移。
- 不清空、覆盖或批量修改现有记录。
- 自动化测试只使用模拟对象或 SQLite 内存数据库。
- 保留系统原有的正常新增行为，例如资源保存、任务发布和学习记录。

### 2.3 必须说明的产品边界

在不增加持久化结构的情况下，可以实现工作流预览、真实数据诊断、资源生成和发布前确认，但不能实现完全可靠的生产级工作流恢复。

原因是生产级工作流需要长期保存：

- 工作流实例和当前阶段。
- 每个阶段的输入、输出和操作人。
- 任务重试次数和错误记录。
- 教师确认、修改和发布记录。
- 学生任务完成状态。
- 学前检测和学后检测结果。
- 画像更新前后的版本差异。

如果这些信息只放在内存中，服务器重启后会丢失。因此，数据库零改动适合第一阶段串联和验证，不适合作为最终产品方案。

## 三、产品核心工作流

### 3.1 完整流程

```text
第一阶段：选择教学对象
课程 → 班级 → 学生 → 目标知识点
        ↓
第二阶段：读取真实学习证据
练习 → 错题 → 编程 → 视频 → 互动 → 画像对话
        ↓
第三阶段：诊断学习问题
掌握程度 → 高频错误 → 前置知识 → 证据可信度
        ↓
第四阶段：制定个性化学习方案
学习目标 → 内容难度 → 资源形式 → 学习顺序 → 检测标准
        ↓
第五阶段：教师确认
接受方案 → 修改方案 → 暂不发布
        ↓
第六阶段：多智能体生成资源
文档智能体 → 习题智能体 → 项目智能体 → 质量检查
        ↓
第七阶段：发布学生任务
资源包 → 截止时间 → 完成要求 → 学习提醒
        ↓
第八阶段：学生学习与检测
阅读资源 → 完成练习 → 编程实践 → 学后检测
        ↓
第九阶段：评估学习效果
正确率 → 用时 → 提示次数 → 错误变化 → 达标判断
        ↓
第十阶段：更新画像和学习路径
更新证据 → 调整可信度 → 生成下一步任务
        └──────────────────→ 进入下一轮工作流
```

### 3.2 工作流不是简单进度条

页面上的流程图只是展示，真正的工作流还必须包含：

- 每个阶段明确的输入和输出。
- 进入下一阶段的条件。
- 当前需要教师、学生还是系统操作。
- 阶段失败后的重试、降级和恢复方式。
- 防止重复生成、重复发布和重复保存的机制。
- 权限检查和操作记录。

## 四、各阶段的产品设计

### 4.1 选择教学对象

教师按照以下顺序进行选择：

```text
课程 → 已分配该课程的班级 → 班级内学生 → 目标知识点
```

系统必须验证：

- 教师是否拥有该班级的管理权限。
- 学生是否属于所选班级。
- 班级是否已分配所选课程。
- 知识点是否属于所选课程。

课程、班级或学生发生变化时，应清空旧诊断、旧方案和旧生成结果，避免数据串线。

### 4.2 读取学习证据

系统只读取与本次课程和知识点有关的数据：

| 数据来源 | 主要内容 | 用途 |
| --- | --- | --- |
| 画像对话 | 学习目标、偏好、可用时间 | 判断学习目标和资源偏好 |
| 练习记录 | 正确率、用时、重复作答 | 判断知识掌握和学习节奏 |
| 错题记录 | 错误知识点、错误类型、频次 | 判断薄弱点和易错模式 |
| 编程提交 | 通过率、提交次数、代码错误 | 判断实践能力和编程困难 |
| 视频记录 | 观看完成率、暂停和回看 | 判断学习投入和内容偏好 |
| 互动记录 | 提问、提示、讨论和反馈 | 判断自主性和互动偏好 |

每条诊断结论都要展示：

- 数据来源。
- 判断依据。
- 样本数量。
- 数据更新时间。
- 证据可信度。
- 数据不足时明确显示“证据不足”。

### 4.3 诊断学习问题

系统不能只输出“基础较弱”等模糊标签，而应定位到具体问题：

```text
事实：最近5道循环边界题答错3道
判断：循环边界控制掌握不足
关联：可能缺少 range 起止规则这一前置知识
可信度：较高，来自练习和编程两类数据
```

诊断结果至少包括：

- 当前目标知识点掌握程度。
- 主要错误类型。
- 可能缺失的前置知识。
- 学习节奏和资源偏好。
- 当前证据是否足以进行个性化教学。

### 4.4 制定个性化学习方案

学习方案需要把画像结论转换为具体教学动作：

| 诊断或画像特征 | 教学动作 |
| --- | --- |
| 前置知识缺失 | 先补前置知识，再学习目标内容 |
| 连续出现同类错误 | 增加错误辨析和纠错练习 |
| 学习节奏偏慢 | 分段讲解，降低单次信息量 |
| 实践能力较强 | 减少基础解释，增加综合项目 |
| 视觉资源偏好证据充分 | 增加流程图和代码执行过程 |
| 应试目标明确 | 增加考点、变式题和易错提示 |

最终形成一张“个性化学习方案”：

| 方案项目 | 示例 |
| --- | --- |
| 当前问题 | 循环边界控制不稳定 |
| 学习目标 | 正确判断起止值、空区间和越界问题 |
| 学习顺序 | 前置知识 → 图解讲解 → 纠错练习 → 编程任务 |
| 资源配置 | 1份讲义、5道练习、1个调试项目 |
| 建议难度 | 基础到中等 |
| 达标标准 | 等价题正确率达到80%，且不依赖提示 |
| 未达标处理 | 补充前置知识并重新检测 |

### 4.5 教师确认

AI不应绕过教师直接发布教学任务。教师需要能够：

- 查看本次方案使用了哪些证据。
- 修改资源数量、难度和学习顺序。
- 删除不适合的生成动作。
- 接受方案并进入生成。
- 暂停本次任务。

教师的修改应当影响后续生成，而不是只修改页面上的文字。

### 4.6 多智能体生成资源

协调智能体根据已确认的方案拆分任务：

```text
协调智能体
├── 文档智能体：生成概念讲解和图解
├── 习题智能体：生成分层练习和学后检测
├── 项目智能体：生成编程实践任务
└── 质量检查：检查知识覆盖、难度和画像适配
```

每个步骤显示：

- 智能体名称和任务。
- 使用的学生特征和知识证据。
- 当前状态和执行耗时。
- 输出摘要。
- 质量检查结果。
- 重试或降级情况。

### 4.7 发布学生任务

生成成功不等于教学完成。教师还需要设置：

- 任务名称和说明。
- 发布对象。
- 开始时间和截止时间。
- 必学资源和选学资源。
- 完成条件。
- 学后检测规则。

发布前必须显示最终预览，防止错误资源直接到达学生端。

### 4.8 学生学习任务

学生端新增“我的个性化学习任务”，只展示学生需要执行的内容：

```text
为什么要学 → 今天学什么 → 按什么顺序学 → 完成标准是什么
```

学生页面应包含：

- 当前学习目标。
- 推荐原因的简明说明。
- 资源学习顺序。
- 当前完成进度。
- 练习和项目入口。
- 学后检测入口。
- 遇到困难时的提示和求助入口。

不应把画像可信度、智能体日志等教师侧技术信息全部暴露给学生。

### 4.9 学后检测和效果评估

学后检测应使用同知识点、难度相近但题目不同的等价任务，避免学生只是记住原题。

评估指标可以包括：

- 正确率变化。
- 平均完成时间变化。
- 提示使用次数变化。
- 同类错误是否减少。
- 编程任务是否独立通过。
- 学习资源是否完成。

需要注意：一次答对不能直接证明已经掌握。系统应结合多次表现、不同题型和一定时间后的保持情况进行判断。

### 4.10 更新画像和后续路径

画像更新页面需要解释：

```text
新增了什么证据
→ 哪个结论发生了变化
→ 可信度为什么提高或降低
→ 下一步学习计划为什么改变
```

可能的下一步包括：

- 达标：进入下一个知识点。
- 基本达标：安排巩固练习。
- 未达标：补充前置知识。
- 证据不足：继续采集学习数据，不立即修改结论。

## 五、工作流状态设计

建议使用明确的状态机，而不是依靠多个页面自行判断：

```text
DRAFT                  草稿
COLLECTING_EVIDENCE    采集证据
DIAGNOSING             诊断中
WAITING_APPROVAL       等待教师确认
GENERATING             生成资源
READY_TO_PUBLISH       等待发布
PUBLISHED              已发布
LEARNING               学习中
WAITING_ASSESSMENT     等待检测
ASSESSING              评估中
UPDATING_PROFILE       更新画像
COMPLETED              本轮完成
PAUSED                 已暂停
NEEDS_ATTENTION        需要人工处理
```

状态转换示例：

- 证据不足：`DIAGNOSING → COLLECTING_EVIDENCE`
- 教师批准：`WAITING_APPROVAL → GENERATING`
- 教师修改：重新计算方案后回到 `WAITING_APPROVAL`
- 资源准备完成：`GENERATING → READY_TO_PUBLISH`
- 学生完成任务：`LEARNING → WAITING_ASSESSMENT`
- 检测未达标：完成画像更新后进入下一轮补偿任务。
- AI暂时不可用：自动重试或使用本地规则保障，必要时进入 `NEEDS_ATTENTION`。

产品目标不是承诺技术永远不失败，而是保证：

- 已完成的数据不会丢失。
- 可以从中断位置继续。
- 不会重复生成或重复发布。
- 用户知道发生了什么以及如何继续。

## 六、核心页面规划

### 6.1 教师端：个性化教学任务工作台

建议采用左侧任务列表、右侧工作区的布局。

右侧按照当前工作流阶段显示：

1. 教学对象和知识点。
2. 学习证据与问题诊断。
3. 个性化学习方案。
4. 教师确认和修改。
5. 智能体生成过程。
6. 资源包预览与发布。
7. 学生完成情况与学习效果。
8. 画像变化和后续建议。

### 6.2 学生端：我的个性化学习任务

学生端强调学习行动，而不是系统技术过程：

1. 当前任务。
2. 推荐原因。
3. 学习顺序。
4. 资源内容。
5. 练习和项目。
6. 完成进度。
7. 学后检测。
8. 下一步安排。

### 6.3 工作流详情时间线

教师可以展开查看每个阶段：

- 阶段输入。
- 系统判断。
- 智能体执行记录。
- 教师操作记录。
- 阶段输出。
- 下一步触发条件。

## 七、权限与安全要求

- 教师只能访问自己负责的课程和班级。
- 学生只能查看发布给自己的任务和资源。
- 修改请求参数不能访问其他班级的学生画像。
- 画像结论必须显示证据来源，不得编造缺失数据。
- AI生成资源必须经过质量检查和发布前确认。
- 同一发布请求必须具有幂等性，避免重复任务。
- 敏感画像信息按角色控制展示范围。
- 自动化测试不得连接开发数据库或生产数据库。

## 八、异常处理与恢复策略

| 场景 | 产品处理方式 |
| --- | --- |
| 学生画像缺失 | 提示需要采集数据，允许生成普通教学资源 |
| 画像证据不足 | 降低可信度，不输出确定性结论 |
| 知识库未启用 | 明确显示未使用知识库，继续使用课程基本信息 |
| 外部模型超时 | 自动重试，仍不可用时启用本地规则保障 |
| 单个智能体异常 | 保留其他完成结果，只补充缺失资源 |
| 页面轮询中断 | 重新进入页面后恢复查询，不重复发起任务 |
| 教师关闭页面 | 服务端继续处理，重新进入后查看当前阶段 |
| 学生未按时完成 | 标记逾期并通知教师，不自动判定学习失败 |
| 学后检测未达标 | 生成补偿方案，不直接修改为“已掌握” |

## 九、分阶段实施计划

### 第一阶段：不修改数据库的真实工作流串联

目标：在现有数据结构上完成教师端发布前闭环。

- 使用真实课程、班级和学生选择。
- 读取真实学习证据并生成诊断摘要。
- 生成结构化个性化学习方案。
- 增加教师确认和方案调整。
- 接入现有多智能体生成过程。
- 增加资源包预览和发布前检查。
- 工作流运行状态暂存在内存中。
- 页面明确提示服务重启后临时流程可能丢失。

验收标准：

- 不修改数据库结构和既有记录。
- 教师不能访问无权限学生。
- 每个诊断结论都可以追溯到学习证据。
- 教师修改方案后，生成策略同步变化。
- AI不可用时仍能得到可继续处理的资源结果。
- 同一次操作不会产生重复生成请求。

### 第二阶段：工作流持久化

前提：单独评审数据模型并获得数据库变更确认。

- 保存工作流实例和阶段事件。
- 保存教师确认和修改记录。
- 支持服务重启后的流程恢复。
- 支持幂等生成与幂等发布。
- 保存学生任务和完成状态。
- 增加操作审计和异常恢复。

验收标准：

- 服务重启后工作流状态不丢失。
- 可以从中断阶段继续。
- 重复点击不会重复发布任务。
- 教师能够查看完整操作历史。

### 第三阶段：学生学习和效果闭环

- 建立学生个性化任务页面。
- 记录资源学习进度。
- 接入练习、编程任务和学后检测。
- 计算学习前后变化。
- 更新画像证据和可信度。
- 根据结果生成下一轮学习任务。

验收标准：

- 教师发布的任务能够准确到达目标学生。
- 学生完成数据能够回到对应工作流。
- 学后检测使用等价任务而不是重复原题。
- 画像变化能够说明新增证据和变化原因。
- 未达标学生能够进入下一轮补偿学习。

### 第四阶段：稳定性和产品体验

- 增加任务搜索、筛选和批量操作。
- 增加通知和截止时间提醒。
- 完善无数据、等待、暂停和异常状态。
- 增加运行监控和性能指标。
- 完成桌面端和移动端适配。
- 开展真实用户试用并收集反馈。

## 十、测试计划

### 10.1 后端测试

- 教师课程、班级和学生权限验证。
- 画像解释服务保持纯计算，不产生意外写入。
- 工作流状态转换条件。
- 同一请求的幂等处理。
- 不同用户的任务状态隔离。
- 模型重试、本地保障和部分资源补全。
- 发布对象和课程关系校验。
- 学后检测结果与画像更新规则。
- 所有测试使用模拟对象或 SQLite 内存数据库。

### 10.2 前端测试

- 课程、班级和学生三级选择。
- 切换教学对象后旧数据正确清空。
- 证据不足和画像缺失提示。
- 教师修改方案后预览同步更新。
- 生成、暂停、恢复和发布按钮状态。
- 页面轮询停止和重新连接。
- 学生任务完成和检测流程。
- 桌面端与移动端无内容重叠。

### 10.3 产品验收场景

```text
场景一：证据充分的学生完成完整个性化流程
场景二：画像缺失时使用普通资源方案
场景三：教师修改AI方案后再生成
场景四：外部AI不可用时继续完成资源准备
场景五：学生未达标后进入补偿学习
场景六：教师尝试访问其他班级学生时被拒绝
场景七：重复点击生成或发布不会产生重复任务
```

## 十一、产品成功指标

不能只统计“生成了多少资源”，还应关注实际使用结果：

| 指标类型 | 指标示例 |
| --- | --- |
| 工作流效率 | 从诊断到发布的平均耗时、教师修改次数 |
| 资源使用 | 资源打开率、完成率、任务按时完成率 |
| 学习表现 | 正确率、耗时、提示次数和重复错误变化 |
| 方案质量 | 教师接受率、教师修改率、资源退回率 |
| 系统稳定性 | 生成恢复率、重复发布率、状态丢失次数 |
| 画像质量 | 有效证据来源数、证据新鲜度、结论稳定性 |

在没有真实用户数据前，这些只能作为待采集指标，不能预先填写或宣称已经提升。

## 十二、近期执行建议

接下来不继续增加新的智能体或独立功能，优先完成以下产品主线：

1. 将教师端现有个性化生成改造成“个性化教学任务工作台”。
2. 接入真实课程、班级、学生和学习证据。
3. 增加可修改、可确认的个性化学习方案。
4. 串联多智能体生成、质量检查和发布前预览。
5. 在不修改数据库的条件下验证完整流程和权限。
6. 单独设计工作流持久化数据模型，评审通过后再修改数据库。
7. 最后接入学生任务、学后检测和画像更新。

最终产品应形成以下稳定闭环：

> 真实学习证据驱动问题诊断，诊断结果形成教师可控的个性化学习方案，多智能体按照方案生成并发布资源，学生学习结果再次成为新的画像证据和后续教学依据。
