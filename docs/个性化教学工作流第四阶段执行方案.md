## 一、第四阶段解决什么

第四阶段是“稳定性和产品体验”，不是继续堆叠智能体数量。第三阶段已经证明工作流能跑通，第四阶段要解决的是：任务多了以后教师找不找得到、学生会不会错过、异常后能不能恢复、系统慢在哪里、真实账号能不能稳定完成全过程。

```text
第三阶段：一次个性化教学闭环能够正确完成
第四阶段：很多教师和学生长期使用时仍然清楚、稳定、可追踪
```

## 二、已经核实的现状

已证实：

- 个性化任务目前只有按发布时间返回的列表，没有分页、关键词搜索和组合筛选。
- 已有 `due_at` 字段和暂停/恢复状态，但没有逾期计算、定时提醒和通知闭环。
- 已有 `AnalysisNotification`，但它的 `related_id` 是整数，不能可靠关联字符串形式的 `delivery_id`。
- 已有 Prometheus 指标基础和 `/api/metrics` 路由，但监控看板响应仍是说明文字，没有工作流成功率、降级率和耗时数据。
- 2026-07-23 生产构建通过，但 `StudentDashboard` 产物约 952 KB，超过构建工具的 500 KB 警戒线。
- 自动化测试已覆盖权限和内存数据库写入，但真实教师、学生账号的完整人工流程尚未验收。

暂时无法确认：

- 生产环境是否长期运行 Celery worker、Celery Beat 和 Redis。代码中存在相关配置，不等于部署环境已经可用。
- 实际并发人数和服务器资源上限。没有压测数据前不能声称系统支持某个固定并发量。

## 三、推进顺序

### 4A：任务运营能力

目标：教师和学生在任务变多以后仍能快速找到当前工作。

怎么做：

1. 教师任务接口增加分页、关键词、课程、班级、学生、状态和日期筛选。
2. 学生任务接口增加待开始、学习中、待检测、已完成和已逾期分组。
3. 前端增加搜索框、筛选菜单、状态标签、结果数量和清空筛选。
4. 本批批量操作限制为“批量暂停/恢复”；批量提醒需要可持久化且可幂等的通知结构，归入 4B；暂不做批量个性化生成，避免不同学生资源串线。
5. 所有批量操作逐条验证教师权限，并返回成功、跳过和不可操作原因。

验收：同一教师有大量任务时可以组合筛选；修改请求参数不能操作其他教师任务；重复批量请求不制造重复事件。

### 4B：截止时间与站内通知

目标：学生知道何时该做什么，教师知道哪些任务需要干预。

怎么做：

1. 先实现读取时计算的 `due_status`：未设置、正常、即将截止、已逾期、已完成。
2. 建立专门的个性化任务通知模型，使用字符串 `delivery_id`，不把数据硬塞进不兼容的 `AnalysisNotification.related_id`。
3. 站内通知覆盖：任务发布、临近截止、已逾期、教师暂停/恢复、系统恢复完成、下一轮方案生成。
4. 定时提醒优先使用 Celery Beat；启动时必须检查 worker、Beat 和 Redis，可用才启用，不可用时页面明确显示“定时提醒未启用”。
5. 通知创建使用唯一幂等键，同一任务、同一提醒窗口只产生一条。

数据库要求：这一部分需要新增通知表或兼容字段，实施前必须备份数据库；只新增结构和新业务记录，不覆盖历史记录。

验收：重复调度不重复通知；逾期不是“任务失败”；外部调度不可用时仍可正常查看任务，并得到通俗提示。

### 4C：异常恢复与可观测性

目标：系统出现外部 AI、网络或进程异常时，不丢任务，并能知道卡在哪里。

怎么做：

1. 统一空数据、加载、暂停、降级、需要恢复和权限不足状态文案。
2. 为发布、测评绑定、效果分析和下一轮创建增加结构化运行指标。
3. 指标至少包括：生成总量、自动修复率、降级率、发布成功率、周期完成率、平均耗时、P95 耗时、恢复次数和权限拒绝次数。
4. 把 `/api/metrics/dashboard` 的说明文字替换为真实聚合数据，并限制管理员或授权教师访问。
5. 检查并修复监控中间件导入路径、异常处理和敏感路由暴露问题。
6. 增加进程重启、重复请求、外部 AI 不可用和任务调度不可用测试。

验收：任一外部服务不可用不会丢失已保存证据；管理页面能定位异常阶段；监控接口不泄露学生作答和画像原文。

### 4D：性能、移动端和真实验收

目标：让产品在真实设备和真实账号上可持续使用。

怎么做：

1. 拆分 `StudentDashboard`，按功能视图动态加载练习、画像、知识图谱和任务中心。
2. 对任务列表、事件和周期接口实施分页，避免一次返回完整历史。
3. 检查慢查询和索引，优化前必须先记录基线，不能凭感觉改数据库。
4. 清理全仓 ESLint 错误和无效旧状态，保留仍在使用的业务逻辑。
5. 使用真实教师和学生账号完成：生成、审核、发布、学习、检测、画像更新、下一轮生成。
6. 检查桌面端和 390×844 移动端，无横向溢出、按钮遮挡和文本重叠。
7. 使用脱敏测试数据进行并发和恢复测试，不对正式学生数据压测。

验收：生产构建无功能回归；关键页面按需加载；真实账号完整流程不依赖接口拦截；发现的问题有复现步骤和处理结果。

## 四、建议实施批次

第一批：4A 任务搜索筛选和 `due_status`，不改数据库结构。

第二批：4B 持久通知和定时任务。该批次涉及数据库新增结构，必须单独备份、迁移和核对。

第三批：4C 真实监控和恢复测试。

第四批：4D 前端拆包、全仓治理、真实账号及移动端验收。

## 五、第四阶段完成标准

- 教师能在大量任务中准确搜索、筛选和批量提醒。
- 学生能看到明确截止状态、站内通知和下一步动作。
- 通知和调度重复执行不会制造重复记录。
- 外部 AI、Redis、Celery 或网络不可用时有降级和恢复路径。
- 监控展示真实工作流指标，不展示占位说明。
- 学生端大包得到实质拆分，移动端主要流程无布局问题。
- 全量后端测试、前端 Jest、ESLint 和生产构建通过。
- 真实教师和学生账号完成一次不使用接口模拟的端到端验收。

## 六、风险边界

- “不能失败”应解释为数据不丢、请求可重试、状态可恢复，而不是声称外部网络和模型永远不会异常。
- 不能用视频观看完成、页面停留时间直接证明知识掌握。
- 批量生成会放大成本、串线和并发风险，必须晚于单学生流程稳定性验证。
- 通知频率需要上限，否则会形成打扰并增加任务队列压力。
- 监控只能记录状态、耗时和匿名计数，不能把学生答案、画像原文或密钥写入指标标签。
