# 个性化教学工作流第三阶段设计方案

更新时间：2026-07-23

## 一、阶段定位

第三阶段解决“资源生成以后发生什么”。目标不是再增加一个生成页面，而是把教师生成的资源真正交给学生，并根据学生的真实学习结果形成下一轮教学方案。

完整闭环：

```text
教师确认资源
→ ReviewAgent自动审核并补齐
→ 发布给指定学生
→ 学生按顺序学习和作答
→ 系统绑定真实练习、错题、编程和视频证据
→ FeedbackAgent分析本轮学习效果
→ ProfileUpdateAgent提出画像变化
→ EvidenceReviewAgent审核变化是否有足够证据
→ 自动形成下一轮教学策略
→ 创建下一轮工作流
```

第三阶段完成后，产品才能从“个性化资源生成器”升级为“持续调整的个性化教学系统”。

## 二、需要先纠正的三个假设

### 2.1 第二阶段没有保存学生任务

早期总方案曾把学生任务保存列入第二阶段，但第二阶段实际只完成了工作流和事件持久化。因此第三阶段必须先建设任务发布，不能直接从生成结果跳到效果评估。

### 2.2 不能只用课程总进度判断本轮效果

现有 `learning_progress` 是课程级进度，不能证明某次个性化资源是否有效。第三阶段必须建立“工作流资源 → 学生任务 → 学习行为 → 原始作答记录”的绑定关系。

### 2.3 “不能失败”应解释为“不能让用户无路可走”

无法保证网络、外部AI和第三方资源永远正常。产品必须保证：

- 外部AI不可用时自动使用本地规则。
- 自动审核无法完成时使用结构检查和固定模板补齐。
- 已提交的数据不丢失。
- 重试不产生重复任务和重复学习周期。
- 页面明确说明当前采用了AI结果还是本地保障结果。

## 三、本阶段边界

### 3.1 本阶段完成

- 教师把审核通过的工作流发布给指定学生。
- 学生端展示个性化学习任务。
- 记录文档、练习、项目和媒体等资源的开始、进度和完成事件。
- 将现有练习、错题、编程提交和视频进度绑定到本次任务。
- 自动计算本轮学习前后变化。
- FeedbackAgent生成学习效果结论。
- ProfileUpdateAgent生成画像变化建议。
- EvidenceReviewAgent自动审核画像变化和下一轮策略。
- 自动创建下一轮工作流草稿。
- 支持刷新、服务重启、重复请求和中断恢复。

### 3.2 本阶段不完成

- 不引入BKT、IRT或深度知识追踪模型。
- 不建设新的练习引擎、视频系统或编程判题器。
- 不用一次作答直接认定长期能力变化。
- 不做跨教师共享、班级批量发布和复杂通知中心。
- 不修复历史数据库已有的外键悬挂记录，该问题单独治理。
- 不自动删除历史任务、学习证据或画像快照。

## 四、复用现有数据

第三阶段不复制原始学习数据，继续读取：

| 现有数据 | 本阶段用途 | 使用限制 |
| --- | --- | --- |
| `practice_evaluations` | 练习分数、作答和评测结果 | 必须校验学生、测评和课程关系 |
| `mistake_records` | 错题类型、频次和掌握状态 | 只使用任务证据窗口内的新记录 |
| `programming_submissions` | 编程通过率、提交次数和错误类型 | 必须关联本次课程和测评 |
| `video_progress` | 视频进度和完成状态 | 只绑定本任务实际包含的视频 |
| `learning_progress` | 课程整体进度背景 | 不能单独作为本轮达标依据 |
| `student_profiles` | 发布前画像基线 | 不允许无证据直接覆盖 |
| `personalized_workflows` | 方案、资源、审核和画像快照 | 发布后资源使用不可变快照 |
| `personalized_workflow_events` | 教师侧流程和状态历史 | 不写入高频学生行为 |

## 五、新增数据模型

本阶段建议新增三张表。只新增表和索引，不修改现有字段。

### 5.1 personalized_task_deliveries

一条记录表示某个工作流资源包发布给一个学生。

| 字段 | 用途 |
| --- | --- |
| delivery_id | 对外任务编号，例如 `dlv_xxx` |
| workflow_id | 来源工作流 |
| owner_id | 发布教师 |
| course_id / class_id / student_user_id | 权限范围和学习对象 |
| status | 当前任务状态 |
| title / instructions | 学生看到的任务名称和说明 |
| resource_snapshot_json | 发布时资源不可变快照 |
| strategy_snapshot_json | 本轮教学策略快照 |
| baseline_snapshot_json | 发布前画像和证据基线 |
| completion_rules_json | 必学资源、达标条件和检测规则 |
| progress_percentage | 本任务整体进度 |
| idempotency_key | 防止重复发布 |
| version | 并发更新版本 |
| published_at / due_at | 发布时间和截止时间 |
| started_at / completed_at | 学生开始和完成时间 |
| created_at / updated_at | 记录时间 |

约束：

- 同一工作流、同一学生、同一发布版本只能有一条有效任务。
- 发布后资源使用快照，后续修改原工作流不能悄悄改变学生已经收到的内容。
- 删除或更新请求不能通过修改参数访问其他教师或其他学生任务。

### 5.2 personalized_delivery_events

只追加学生学习事件，不覆盖历史行为。

| 字段 | 用途 |
| --- | --- |
| id | 内部主键 |
| delivery_id | 所属学生任务 |
| student_user_id | 实际学习学生 |
| event_type | `task_started`、`resource_opened`、`progress_updated`、`resource_completed`、`assessment_bound`等 |
| resource_key | 工作流资源中的稳定编号 |
| event_data_json | 进度、时长、来源记录编号等结构化数据 |
| idempotency_key | 防止前端重试重复写入 |
| occurred_at | 客户端事件时间 |
| received_at | 服务端接收时间 |

约束：

- 客户端只能提交允许的事件类型和有限字段。
- 服务端重新校验当前学生是否拥有该任务。
- 分数、正确率和判题结果不能由前端自由填写，只能引用后端已有记录。
- 高频进度事件按资源和时间窗口合并，避免无限增长。

### 5.3 personalized_learning_cycles

一条记录表示一次任务完成后的效果分析和下一轮决策。

| 字段 | 用途 |
| --- | --- |
| cycle_id | 对外学习周期编号，例如 `cyc_xxx` |
| delivery_id / workflow_id | 来源任务和工作流 |
| cycle_number | 第几轮个性化教学 |
| status | 收集证据、分析、审核、完成或需要继续处理 |
| evidence_window_start / end | 本轮只读取这个时间范围内的新证据 |
| evidence_snapshot_json | 原始证据编号、摘要和来源 |
| assessment_snapshot_json | 学后检测和等价任务结果 |
| feedback_json | FeedbackAgent学习效果结论 |
| profile_before_json | 分析前画像快照 |
| profile_proposal_json | ProfileUpdateAgent变化建议 |
| profile_after_json | 自动审核后的本轮有效画像快照 |
| review_json | EvidenceReviewAgent审核结果 |
| next_strategy_json | 下一轮教学动作 |
| next_workflow_id | 自动创建的下一轮工作流 |
| tracking_id | Agent执行追踪编号 |
| idempotency_key | 防止重复分析和重复创建下一轮 |
| created_at / updated_at / completed_at | 生命周期时间 |

说明：

`profile_after_json` 是本轮策略使用的快照，不等于无条件覆盖 `student_profiles`。只有通过自动证据门槛的稳定结论才允许同步到永久画像，其余结论保留为“待观察”。

## 六、状态机扩展

### 6.1 教师工作流状态

在第二阶段状态基础上增加：

```text
READY_TO_PUBLISH
→ PUBLISHED
→ LEARNING
→ WAITING_ASSESSMENT
→ ASSESSING
→ UPDATING_PROFILE
→ COMPLETED
```

异常分支：

```text
ASSESSING / UPDATING_PROFILE
→ NEEDS_ATTENTION
→ 原阶段重试
```

### 6.2 学生任务状态

```text
PUBLISHED          已发布未开始
IN_PROGRESS        学习中
WAITING_ASSESSMENT 学习资源完成，等待检测
ASSESSING          正在分析
CYCLE_COMPLETED    本轮完成
OVERDUE            已逾期但仍可继续
PAUSED             已暂停
NEEDS_ATTENTION    数据异常，系统正在恢复
```

逾期不等于学习失败，不得因为超过截止时间直接生成“未掌握”结论。

## 七、Agent职责

### 7.1 ReviewAgent

发布前执行：

- 检查必需资源是否齐全。
- 检查知识点覆盖和学习顺序。
- 检查练习是否有答案和解析。
- 检查项目是否有步骤和验收标准。
- 检查外部链接是否可访问。
- 自动修复缺项并再次审核。
- 外部AI不可用时使用结构规则和本地模板补齐。

ReviewAgent不负责判断学生是否掌握。

### 7.2 FeedbackAgent

输入：

- 发布前基线。
- 本任务完成事件。
- 新增练习、错题、编程和视频证据。
- 学后检测结果。

输出：

```json
{
  "learning_effect": "partially_improved",
  "evidence": [],
  "improvements": [],
  "remaining_problems": [],
  "confidence_score": 0,
  "next_actions": []
}
```

FeedbackAgent只总结本轮变化，不直接修改学生画像。

### 7.3 ProfileUpdateAgent

将本轮效果转成画像变化建议：

```text
旧结论
→ 本轮新增证据
→ 建议的新结论
→ 可信度变化
→ 影响的下一轮策略
```

### 7.4 EvidenceReviewAgent

自动审核画像变化和下一轮策略，不需要教师逐条批准。

审核规则：

- 是否引用真实存在的证据编号。
- 证据是否属于当前学生、课程和时间窗口。
- 是否至少有两个独立来源相互支持。
- 是否存在练习、编程或学后检测之间的冲突。
- 是否把一次答对误判为长期掌握。
- 下一轮策略是否确实对应剩余问题。

自动处理：

| 结果 | 系统动作 |
| --- | --- |
| 高可信度 | 形成新的有效画像快照，可按白名单同步稳定字段 |
| 中可信度 | 标记“待观察”，用于下一轮保守策略，不覆盖永久画像 |
| 低可信度 | 不改变画像结论，继续收集数据 |
| 证据冲突 | 同时展示冲突，不强行得出单一结论 |

## 八、画像自动更新门槛

第一版使用可解释规则，不引入BKT。

永久画像自动同步必须同时满足：

- 至少两个独立证据来源。
- 至少五个有效样本，或一个完整项目加一组等价检测。
- 证据都在本轮有效时间窗口内。
- EvidenceReviewAgent审核通过。
- 可信度不低于80。
- 新旧证据不存在明显冲突。
- 字段属于允许自动同步的白名单。

以下字段第一版不建议自动覆盖：

- 长期学习目标。
- 职业方向。
- 稳定认知风格。
- 教师人工确认的信息。

以下内容可以优先形成周期快照：

- 当前知识薄弱点。
- 当前任务掌握程度。
- 最近学习节奏。
- 提示依赖情况。
- 下一轮资源难度和学习顺序。

## 九、后端接口

### 9.1 教师发布与查看

```http
POST /api/resource-generation/workflow/{workflow_id}/publish
GET  /api/resource-generation/workflow/{workflow_id}/deliveries
GET  /api/personalized-deliveries/{delivery_id}
POST /api/personalized-deliveries/{delivery_id}/pause
POST /api/personalized-deliveries/{delivery_id}/resume
```

发布请求包含截止时间、必学资源和完成规则。后端重新检查教师、班级、学生、课程和工作流归属。

### 9.2 学生任务

```http
GET  /api/student/personalized-deliveries
GET  /api/student/personalized-deliveries/{delivery_id}
POST /api/student/personalized-deliveries/{delivery_id}/start
POST /api/student/personalized-deliveries/{delivery_id}/events
POST /api/student/personalized-deliveries/{delivery_id}/complete-resource
POST /api/student/personalized-deliveries/{delivery_id}/submit-assessment
```

学生接口忽略客户端传入的 `student_user_id`，始终使用当前登录用户。

### 9.3 效果分析与下一轮

```http
POST /api/personalized-deliveries/{delivery_id}/analyze
GET  /api/personalized-learning-cycles/{cycle_id}
GET  /api/resource-generation/workflow/{workflow_id}/feedback
POST /api/personalized-learning-cycles/{cycle_id}/next-workflow
```

`analyze` 和 `next-workflow` 都使用幂等键。同一任务只能生成一个相同轮次的分析结果和下一轮工作流。

## 十、页面设计

### 10.1 教师端

在个性化教学工作台增加三个阶段区域。

#### 发布设置

- 发布学生和资源清单。
- 必学与选学资源。
- 截止时间。
- 完成条件。
- ReviewAgent最终审核结果。
- 发布按钮和发布结果。

#### 学习进展

- 未开始、学习中、等待检测和已完成状态。
- 资源完成进度。
- 练习、编程和视频摘要。
- 逾期、证据不足和数据异常提示。

#### 效果与下一轮

```text
发布前问题
→ 本轮采用策略
→ 学生真实表现
→ 已改善和未改善问题
→ 画像变化建议
→ 下一轮教学动作
```

### 10.2 学生端

新增“个性化学习任务”页面，第一屏直接是任务，不制作宣传页。

页面包含：

- 当前目标和通俗推荐原因。
- 按顺序排列的学习资源。
- 每项资源的完成状态。
- 练习和编程入口。
- 学后检测入口。
- 总进度和下一步动作。

学生端不显示Agent内部提示词、完整画像标签和教师审计日志。

## 十一、学习效果计算

第一版采用透明规则，分别计算事实和结论。

事实指标：

- 任务资源完成率。
- 学前与学后等价检测正确率。
- 平均完成时间变化。
- 提示使用次数。
- 同类错题变化。
- 编程提交次数和首次通过情况。
- 延迟检测结果。

结论类型：

| 结论 | 判断方式 |
| --- | --- |
| 明显改善 | 多类证据均改善，且学后检测达标 |
| 部分改善 | 部分指标改善，但仍有稳定错误 |
| 暂无改善 | 有足够样本但主要指标没有改善 |
| 证据不足 | 样本量不足或任务未完整完成 |
| 证据冲突 | 不同来源给出相反信号 |

“证据不足”不能写成“学习失败”，“暂无改善”也不能直接推断学生能力低。

## 十二、下一轮工作流生成

下一轮不是复制上一轮资源，而是根据剩余问题创建新的 `DRAFT` 工作流：

```text
上一轮已掌握内容 → 降低重复讲解比例
仍然错误的知识点 → 增加针对性练习
提示依赖较高 → 增加逐步撤除提示的任务
基础达标但迁移不足 → 增加综合项目
证据冲突 → 安排短检测，不扩大结论
```

新工作流必须保存：

- 来源 `cycle_id`。
- 上一轮证据快照。
- 采用和拒绝了哪些画像变化建议。
- 下一轮策略与具体资源动作。

## 十三、数据安全与权限

- 教师只能发布自己工作流中的资源。
- 教师只能查看自己班级学生的任务和结果。
- 学生只能查看和操作自己的任务。
- 管理员权限沿用现有角色策略，但所有读取保留审计记录。
- 学生行为接口不接受任意分数和画像结论。
- 原始证据通过后端查询获得，不能由前端伪造。
- 资源快照和画像快照不能包含密码、会话、API密钥或完整提示词。
- 所有自动化测试继续使用SQLite内存数据库或临时数据库。

## 十四、异常和降级策略

| 场景 | 处理方式 |
| --- | --- |
| 外部AI不可用 | FeedbackAgent和审核Agent改用本地规则，保留来源说明 |
| 外部资源不可访问 | 发布前移除或替换，学生端不展示无效入口 |
| 学生重复点击完成 | 幂等返回原事件，不重复累计进度 |
| 页面离线后重连 | 按服务端事件恢复，不用客户端缓存覆盖进度 |
| 学生只完成部分资源 | 保留真实进度，不提前进入效果分析 |
| 检测记录缺失 | 标记证据不足，不生成掌握结论 |
| Agent中断 | 周期进入可恢复状态，保留已收集证据 |
| 单个数据源异常 | 排除异常来源，其他证据继续分析 |
| 学生逾期 | 显示逾期但允许继续，不自动判定未掌握 |
| 下一轮创建重复 | 返回已存在工作流，不重复创建 |

## 十五、安全升级方案

新增独立升级器：

```bash
python scripts/migrate_personalized_workflow_phase3.py
python scripts/migrate_personalized_workflow_phase3.py --apply
```

执行要求：

1. 默认只检查，不修改数据库。
2. 先在临时SQLite验证升级、重复升级和回滚。
3. 真实数据库升级前自动备份。
4. 只创建本阶段三张表和索引。
5. 升级前后逐表比对原有记录数量。
6. 比对升级前后已有外键问题，确保没有新增。
7. 禁止执行仓库中包含删表操作的旧 Alembic 全量迁移。

回滚只允许删除本阶段三张新表，不修改工作流、课程、学生和画像等原有表。

## 十六、实施顺序

### 模块一：发布和任务持久化

- 建立三张新表和安全升级器。
- 扩展工作流状态机。
- 实现ReviewAgent发布前审核。
- 实现幂等发布和权限校验。

验收：教师只能发布审核通过的本人工作流，重复点击不产生重复任务。

### 模块二：学生任务中心

- 增加学生任务列表和详情。
- 展示推荐原因、资源顺序和完成条件。
- 记录开始、打开、进度和完成事件。
- 支持桌面和移动端。

验收：学生只能看到自己的任务，刷新和重启后进度不丢失。

### 模块三：检测与证据绑定

- 绑定现有练习、错题、编程和视频记录。
- 建立证据时间窗口和来源编号。
- 增加学后等价检测。
- 防止前端伪造分数和结论。

验收：每个效果结论都能追溯到真实数据库记录。

### 模块四：反馈与画像变化

- 实现FeedbackAgent。
- 实现ProfileUpdateAgent。
- 实现EvidenceReviewAgent自动审核和本地降级。
- 形成周期画像快照和下一轮策略。

验收：证据不足不改变永久画像，冲突证据不会被强行合并。

### 模块五：下一轮闭环

- 自动创建下一轮工作流草稿。
- 展示前后证据、画像和策略差异。
- 保证下一轮创建幂等。
- 教师端展示完整学习周期。

验收：不同学生结果产生不同下一轮策略，并能说明原因。

### 模块六：全量验证

- 后端权限、状态机、幂等、恢复和Agent降级测试。
- 前端学生任务、进度、反馈和移动端测试。
- 临时数据库升级与回滚测试。
- 真实数据库备份、升级和完整性核对。
- 后端全量测试、前端Jest、阶段文件ESLint和生产构建。
- Chrome桌面和移动视口页面检查。

## 十七、测试矩阵

### 17.1 后端

- 其他教师不能发布或查看工作流任务。
- 学生不能通过修改参数读取他人任务。
- 重复发布只生成一条任务。
- 重复学习事件只记一次。
- 伪造分数和错误的原始记录编号被拒绝。
- 学生部分完成时不触发最终分析。
- FeedbackAgent外部AI不可用时使用本地规则。
- EvidenceReviewAgent拒绝无来源画像变化。
- 同一周期只创建一个下一轮工作流。
- 服务中断后可以从原状态恢复。

### 17.2 前端

- 教师发布设置和按钮状态。
- 学生任务列表、详情、空状态和逾期状态。
- 资源完成后进度正确变化。
- 页面刷新后使用服务端真实进度。
- 学后检测等待、完成和证据不足展示。
- 教师端前后变化因果链。
- 外部AI降级来源提示。
- 桌面和移动端无重叠、截断和横向溢出。

### 17.3 产品场景

```text
场景一：学生完整完成任务并达标，生成进阶工作流
场景二：学生部分改善，生成巩固工作流
场景三：学生未完成检测，只显示证据不足
场景四：练习改善但编程没有改善，显示证据冲突
场景五：外部AI不可用，本地规则完成分析和下一轮方案
场景六：教师重复发布、学生重复提交，均不产生重复记录
场景七：其他教师和其他学生尝试越权访问时被拒绝
场景八：服务重启后任务、进度、周期和下一轮工作流均能恢复
```

## 十八、完成定义

第三阶段只有同时满足以下条件才算完成：

- 工作流资源能准确发布给指定学生。
- 学生能在独立任务中心完成资源和检测。
- 学习行为与原始练习、错题、编程和视频记录能正确绑定。
- 每个学习效果结论都展示事实、来源、样本和可信度。
- 画像变化经过自动证据审核，不能由模型自由覆盖。
- 外部AI不可用时仍能完成可解释的本地分析。
- 不同学习结果能生成不同下一轮策略。
- 所有写入支持幂等、权限隔离和中断恢复。
- 新表升级不改变任何原有表的记录数量。
- 后端和前端自动化测试无失败，生产构建通过。

## 十九、最终产品表现

第三阶段完成后，用户看到的不再是一次性的AI生成，而是一个持续运行的教学循环：

> 系统根据真实证据诊断学生问题，生成并发布针对性资源；学生完成学习后，系统再依据真实结果判断哪些问题改善、哪些仍需处理，并自动形成有证据支持的下一轮教学方案。
