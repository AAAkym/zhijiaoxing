# 本次对话项目更新总览

更新时间：2026-07-23

## 一、这次对话最终解决了什么

这次改造最开始讨论的是两个问题：

1. 学生画像虽然存在，但用户看不出画像是怎样得出的，也看不出画像如何影响资源生成。
2. 页面只展示生成结果，没有完整呈现多个 Agent 的生成、审核、修复和发布过程。

经过多轮分析后，产品方向从“增加几个展示模块”升级为一条完整的个性化教学工作流：

```text
学生学习事实
→ 可解释学生画像
→ 个性化教学策略
→ 多 Agent 生成课程资源
→ ReviewAgent 自动审核和修复
→ 教师发布给指定学生
→ 学生学习并完成检测
→ 系统审核学习证据
→ 更新可信画像证据
→ 自动形成下一轮教学策略
```

本次不是只完成了一张演示页面，而是把画像、生成、审核、发布、学习反馈、通知、监控和恢复逐步连接成了产品流程。

## 二、学生画像透明化改造

### 2.1 画像解释方式

画像页面改成三层结构：

| 层级 | 展示内容 | 通俗解释 |
| --- | --- | --- |
| 事实层 | 练习、错题、编程、视频、互动等记录 | 学生实际做过什么 |
| 特征层 | 八维画像、数据来源、判断依据和可信度 | 系统怎样得出当前判断 |
| 策略层 | 资源形式、难度、讲解深度和学习顺序 | 这个判断怎样影响教学 |

完整度和可信度已经分开：

- 完整度表示八个画像维度填写了多少。
- 可信度表示当前结论有多少真实证据支持。
- 数据不足时显示“证据不足”，不生成虚假高分。
- 原来容易被误解成能力分数的雷达图改为“画像证据可信度”。

### 2.2 数据库保护

查看画像页面不会为了显示页面自动创建画像记录。学生没有画像时，接口返回临时空画像，不写数据库。

画像解释使用现有练习、错题、编程、视频、互动和画像数据进行实时计算。自动化测试使用模拟对象或内存数据库，不连接开发数据库。

### 2.3 编程行为画像

编程行为被纳入画像证据，但不会简单把“提交过代码”解释为“已经掌握”。系统关注的是可验证的编程提交、正确性、错误类型和相关知识点。

一次编程结果不能覆盖学生的长期认知风格、兴趣、目标或学习节奏。只有经过证据审核的客观字段才允许进入画像白名单。

## 三、画像驱动的教师生成流程

教师端增加了“课程 → 班级 → 学生”三级选择：

- 课程改变后会重置班级、学生、旧方案和旧结果。
- 只显示已经分配该课程的班级。
- 只允许选择该班级中的学生。
- 后端重新校验教师归属、班级成员关系和课程分配关系。
- 修改请求参数不能读取其他教师班级中的学生。

选择学生后，系统读取真实画像和证据摘要，再输出：

```text
画像特征
→ 生成动作
→ 受到影响的具体资源
```

学生没有可靠画像时，不会伪造个性化特征，而是使用通用方案。教师仍可选择本次允许使用的练习、错题等客观事实。

## 四、多 Agent 生成与自动审核

### 4.1 六阶段生成过程

一次生成使用同一个 `tracking_id` 跟踪六个阶段：

1. 读取学生画像。
2. 检索课程知识库。
3. 协调 Agent 制定策略。
4. 各资源 Agent 并行生成。
5. 一致性和质量检查。
6. 整合个性化资源包。

页面展示 Agent 名称、任务、使用的画像特征、知识点摘要、状态、输出摘要、执行耗时和异常原因。

RAG 没有启用时显示“跳过”，不会误报成执行成功。外部 AI 或外部资源不可用时，系统返回明确提示，并使用本地规则补齐可编辑资源。

### 4.2 ReviewAgent

新增 ReviewAgent 自动审核生成结果：

- 检查固定资源结构是否完整。
- 检查内容与主题、知识点和学生策略是否一致。
- 发现缺项或不一致时自动修复。
- 最多自动修复两轮，避免无限循环。
- 结构必须完整，语义审核达到要求后才允许进入提交或发布流程。

### 4.3 真实部分异常处理

产品中的“不能失败”没有被解释为网络和外部模型永远不会异常，而是实现为：

- 一个资源 Agent 异常时保留其他已经生成的资源。
- 不丢失已经保存的证据和工作流状态。
- 重试不会重复创建工作流、通知、任务或学习周期。
- 页面说明具体卡在哪一步，并提供恢复路径。

最终资源增加完整因果链：

```text
错题或评测证据
→ 薄弱点判断
→ 生成策略
→ 资源中的具体变化
```

## 五、个性化教学工作流四个阶段

### 5.1 第一阶段：发布前闭环

完成教师端的方案制定和资源生成：

- 选择课程、班级和学生。
- AI 结合课程上下文拆分知识点。
- 教师选择允许使用的学习证据。
- 查看“证据 → 动作 → 资源”方案。
- 查看六阶段 Agent 执行过程。
- ReviewAgent 自动审核和修复。
- 只有教师明确点击保存或提交时才执行原有业务写入。

第一阶段数据库结构没有变化。

### 5.2 第二阶段：工作流持久化与恢复

新增：

- `personalized_workflows`：保存工作流、方案、生成结果、审核结果和当前状态。
- `personalized_workflow_events`：保存创建、修订、生成、审核、暂停和恢复事件。

教师刷新页面或服务重启后，可以从“最近工作流”继续原来的流程。重复生成使用数据库条件更新抢占，同一工作流只允许一个请求进入生成状态。

第二阶段采用独立安全迁移脚本，没有执行包含危险删除操作的旧全量迁移。

### 5.3 第三阶段：学生学习反馈闭环

新增：

- `personalized_task_deliveries`：保存发布给学生的任务快照。
- `personalized_delivery_events`：追加记录学习开始、进度、完成和检测事件。
- `personalized_learning_cycles`：保存本轮证据、Agent 结论、画像审核和下一轮策略。

发布资源时会创建并绑定本轮 `Assessment`。学生完成指定检测后，系统通过 FeedbackAgent、ProfileUpdateAgent 和 EvidenceReviewAgent 审核证据。

系统明确区分：

- 看过资源、视频进度属于行为证据，不能直接证明掌握。
- 练习、错题和编程结果属于能力评测证据，可以支持掌握判断。

证据不足时不下结论；练习和编程证据冲突时进入复核，不覆盖永久画像。只有高可信客观结论允许写入画像白名单，并成为下一轮工作流的输入。

### 5.4 第四阶段：任务运营、通知、监控和性能

第四阶段分为 4A、4B、4C、4D，四个批次均已完成代码实施。

4A 任务运营：

- 教师和学生任务搜索、筛选和分页。
- 截止状态实时计算。
- 教师批量暂停和恢复。
- 每条操作重新校验所有权并保持幂等。

4B 通知提醒：

- 新增 `personalized_task_notifications`。
- 支持发布、临期、逾期、暂停、恢复、手动提醒和下一轮就绪通知。
- 学生可单条已读或全部已读。
- 教师可批量手动提醒自己的任务。
- Celery Beat 定期检查临期任务；调度不可用时不影响手动提醒。

4C 真实监控：

- 管理员新增“工作流监控”。
- 展示生成量、自动修复、降级、发布率、周期完成率、耗时、恢复次数和权限拒绝次数。
- 教师监控只包含本人数据，管理员查看系统范围。
- 健康检查真实检测数据库、Redis、Celery Worker 和 Beat。
- 监控不记录学生答案和画像原文。

4D 性能与质量：

- 学生首页的练习、画像、知识图谱、AI 助教、错题、笔记和任务改为按需加载。
- `StudentDashboard` 生产包从约 954 KB 降到 45.91 KB，下降约 95.2%。
- 修复条件 Hook、虚拟列表重名、错题反馈状态回调和 `switch case` 作用域问题。
- ESLint 从 581 个错误降到 0 个错误，仍保留 193 条可见警告。

## 九、仍然存在的限制

以下内容没有被伪装成已经完成：

1. 当前开发环境没有启用 Redis、Celery Worker 和 Celery Beat。自动定时提醒不可用，但页面会明确提示，任务列表和手动提醒仍可用。
2. 尚未使用脱敏业务数据进行并发压测，因此不能声称系统支持某个固定并发人数。
3. 为遵守不随意修改开发库业务记录的要求，没有在开发库创建演示任务走完整的新业务链；完整链路由隔离数据库自动化测试覆盖。
4. 全仓仍有 193 条 ESLint 历史警告，主要是旧模块未使用变量、Hook 依赖和 Fast Refresh 文件组织问题。
5. 生产构建仍提示共享 UI、代码编辑器、Mermaid 和 3D 知识图谱等独立功能块超过 500 KB。
6. SQLAlchemy 旧式查询和 `datetime.utcnow()` 存在弃用警告，需要后续兼容升级。
7. 数据库原有 66 条外键悬挂记录仍需单独治理，不能在没有数据业务确认的情况下直接修复。
