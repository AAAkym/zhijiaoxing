# 个性化教学工作流第二阶段设计方案

更新时间：2026-07-23

## 一、阶段目标

第二阶段只解决“工作流可以长期保存、恢复、追踪和防重复”问题，不提前实现第三阶段的学生任务与学后检测。

完成后的流程：

```text
教师创建方案
→ 工作流和画像快照写入数据库
→ 每次状态变化写入事件时间线
→ Agent生成和ReviewAgent结果写入工作流
→ 服务重启后读取同一工作流继续
→ 重复生成、保存、提交不会产生重复业务记录
```

## 二、已确认的现状与风险

已证实的事实：

- 第一阶段工作流只存在服务器内存中，服务重启后丢失。
- 项目启动时调用 `db.create_all()`，可以创建新表，但不能替代可审计的数据库升级流程。
- 仓库已有 Alembic 初始迁移的 `upgrade()` 会删除课程、学习进度、考核和教学内容表。

因此第二阶段禁止执行：

```bash
alembic upgrade head
```

本阶段使用独立安全升级器，只创建本方案定义的两张新表。SQLite 文件数据库升级前自动备份；升级器可以重复执行，不修改已有业务表和记录。

## 三、数据模型

### 3.1 personalized_workflows

保存工作流当前快照，一条记录代表一次教师针对一个学生和课程的个性化资源流程。

| 字段 | 用途 |
| --- | --- |
| workflow_id | 对外工作流编号，例如 `wf_xxx` |
| owner_id | 创建并管理该流程的教师 |
| course_id / class_id / student_user_id | 本次教学对象范围 |
| state | 当前状态 |
| mode / topic | 通用或个性化模式、教学主题 |
| payload_json | 课程、知识点、证据、画像快照和已确认策略 |
| plan_json | 当前方案快照 |
| generation_json | Agent生成资源及执行说明 |
| review_json | ReviewAgent审核和修复结果 |
| tracking_id | 本次真实Agent追踪编号 |
| draft_config_id | 已保存草稿对应的现有配置记录 |
| review_submitted | 是否已提交现有AI审核流程 |
| version | 乐观并发版本号 |
| last_error | 最近一次需要恢复的错误 |
| created_at / updated_at / completed_at | 生命周期时间 |

不单独拆分资源表的原因：第二阶段关注工作流恢复，资源仍作为一次生成结果的不可变快照。第三阶段发布学生任务时再建立发布快照，避免现在建立无法验证的表结构。

### 3.2 personalized_workflow_events

保存只追加的操作时间线，不覆盖历史事件。

| 字段 | 用途 |
| --- | --- |
| workflow_id | 所属工作流 |
| owner_id / actor_id | 工作流所有者和实际操作人 |
| event_type / stage | 事件类型和业务阶段 |
| from_state / to_state | 状态变化前后 |
| message | 面向教师的通俗说明 |
| event_data_json | 本次事件的结构化补充数据 |
| idempotency_key | 防止同一操作重复写入 |
| created_at | 事件发生时间 |

## 四、状态机

```text
DRAFT
→ WAITING_APPROVAL
→ GENERATING
→ READY_TO_PUBLISH

GENERATING → NEEDS_ATTENTION
NEEDS_ATTENTION → GENERATING

WAITING_APPROVAL / NEEDS_ATTENTION / READY_TO_PUBLISH
→ PAUSED
PAUSED → WAITING_APPROVAL
```

约束：

- 只有工作流所有者可以读取和修改。
- 生成开始使用数据库条件更新抢占执行权，防止两个请求同时生成。
- 已存在生成结果时直接返回原结果。
- 已保存草稿或已提交审核时直接返回原记录。
- 服务异常中断后，长时间停留在 `GENERATING` 且没有结果的流程会转为 `NEEDS_ATTENTION`，教师可以继续生成。
- 每次状态变化同时写入事件表。

## 五、接口变化

保留第一阶段接口并向后兼容：

```http
POST /api/resource-generation/workflow/plan
POST /api/resource-generation/workflow/{id}/generate
GET  /api/resource-generation/workflow/{id}
POST /api/resource-generation/workflow/{id}/save-draft
POST /api/resource-generation/workflow/{id}/submit-review
```

新增：

```http
GET  /api/resource-generation/workflows
POST /api/resource-generation/workflow/{id}/pause
POST /api/resource-generation/workflow/{id}/resume
```

重新调整证据时，前端传回原 `workflow_id`，后端更新同一个工作流并新增方案修订事件，不再生成无意义的重复工作流。

## 六、权限与数据安全

- 列表查询固定使用当前登录教师的 `owner_id`。
- 单条读取、生成、暂停、恢复、保存和提交都同时验证 `workflow_id + owner_id`。
- 创建和更新方案仍调用课程、班级、学生三重权限校验。
- JSON快照不包含登录凭证、密码或外部AI密钥。
- 升级器只创建新表；回滚只删除这两张新表，不修改原业务表。

## 七、升级与回滚

安全升级器：

```bash
python scripts/migrate_personalized_workflow_phase2.py --apply
```

执行顺序：

1. 解析当前配置的数据库地址。
2. SQLite 自动复制数据库文件到带时间戳的备份文件。
3. 检查两张表是否已经存在。
4. 只创建缺失的工作流表和索引。
5. 再次检查表结构并输出结果。

回滚必须显式执行：

```bash
python scripts/migrate_personalized_workflow_phase2.py --rollback --apply
```

回滚会先备份，再删除事件表和工作流表。工作流数据会丢失，但课程、学生、画像、资源和审核等原有表不受影响。

## 八、验收标准

- 服务重启后可以读取工作流快照和完整事件时间线。
- 教师只能看到自己创建的工作流。
- 重新制定方案更新原工作流，不产生重复工作流。
- 并发或重复生成只执行一次。
- 重复保存草稿和提交审核不产生重复记录。
- 中断的生成流程可以恢复为“需要处理”并再次生成。
- 暂停和恢复遵守状态机，非法跳转返回通俗错误。
- 升级和回滚只影响两张新增表。
